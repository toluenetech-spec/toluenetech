2. AUTHENTICATION FLOW (Admin)
--------------------------------------------------------------------------------
Frontend context/AuthContext.tsx:
  - Hardcoded ADMIN_PASSWORD const: 'iloveesther221@@'
    (NOTE: there is server-side support for ADMIN_PASSWORD env override via
    server/src/lib/auth.ts, but the frontend context still hardcodes the old one
    — so the admin UI can ONLY log in with the hardcoded password; the env
    override only affects API calls that send X-TT-Admin-Password directly.)
  - Session persistence: sessionStorage key 'tt_admin_session' = password in plaintext.
  - login(pass): boolean; logout() clears sessionStorage.
  - role: 'admin' | null.
  - No Firebase Auth is wired in (useAuth() is password-only; Firebase is imported
    but only attempted from ToleshChat for Bearer token, and currentUser will be null
    because no login page calls signInWithEmailAndPassword / signInWithPopup).

Login screen (pages/Admin.tsx):
  - Single password input, "Login" button.
  - Error modal "Incorrect Password" with Retry button (shown when login() returns false).
  - Success modal: green checkmark "Welcome Admin / Connecting to Firebase..."
    uses setTimeout(() => setLoginStatus('idle'), 1500) inside JSX (side effect in render — bug).
  - Post-login: renders full Control Center.

Server auth (server/src/lib/auth.ts):
  authAdmin(req, env):
    1) Bearer JWT: decodes payload; checks exp, aud, iss, sub; looks up uid in admin_users.
       NOTE: signature is NOT verified (JWT is accepted structurally; comment says
       full RSA-SHA256 verification is future work).
    2) X-TT-Admin-Password header: compared to env.ADMIN_PASSWORD || 'iloveesther221@@'.
    3) Otherwise throws.
  authClient(req, env):
    1) Bearer JWT (same caveat) → looks up userId in clients.
    2) X-TT-Client-Email + X-TT-Client-Code → demo@toluenetech.com / DEMO-2026
       → returns {uid:'client-demo', clientId:'client-demo', …}.
    3) X-TT-Client-Demo: 1 → same demo identity.

How ToleshChat authenticates as admin (components/ToleshChat.tsx):
  - Reads sessionStorage.getItem('tt_admin_session') and sends it as X-TT-Admin-Password.
  - Also tries firebase.auth.currentUser.getIdToken() for Bearer (no-op since not logged in).
  - So the admin copilot authenticates using the SAME hardcoded password the user
    typed to enter /admin — stored in plaintext in sessionStorage.

6. DATA SOURCES / BACKEND CONNECTIONS
--------------------------------------------------------------------------------
The admin UI is currently wired to TWO data layers that are NOT in sync:

(a) Firebase (frontend DataContext.tsx) — THIS IS WHAT THE ADMIN UI READS/WRITES
    - db imported from ../firebase (Firestore)
    - storage imported from ../firebase (Storage)
    - Collections used:
        projects, services, solutions, products, labs, testimonials, faqs,
        insights, leads, clients, clientProjects, milestones, files, messages,
        media, settings/global (single doc)
    - addLead() also fires-off a POST to /leads on the Worker (lib/api.ts
      submitLead) to write a parallel record into Neon with a server-generated
      TT-xxxx ref. If the Worker returns a ref, the Firebase copy's reference
      field is overwritten. Failure is silently swallowed ("/* ignore */").
    - All uploads (project images, project video, brand assets, founder image,
      media library files) → Firebase Storage via uploadBytes / getDownloadURL.

(b) Neon Postgres via Drizzle (backend) — THIS IS WHAT TOLESH/CMS/AI-LAB READ
    - 22 tables in server/src/db/schema.ts: site_settings, services, projects,
      products, lab_items, testimonials, faqs, insights, pricing_plans, leads,
      clients, client_projects, milestones, tasks, project_files, messages,
      invoices, media, assistant_sessions, assistant_messages, admin_users,
      notifications.
    - Endpoints that read/write Neon: /cms/* (read), /leads (POST),
      /assistant/* (read/write sessions/messages/leads), /ai-lab/* (read via tools),
      /media/* (read/write media table + R2).
    - Tolesh's retrieval and tools read from the Neon services/projects/faqs/
      pricing_plans/testimonials tables. Admin copilot stats read Neon leads.
    - The admin UI does NOT display any Neon data; changes made in the admin UI
      (projects, leads) do NOT update Neon, except that new leads from contact
      forms get dual-written. Edits in the admin UI will NOT appear in Tolesh
      answers or /cms responses unless separately seeded into Neon.

(c) R2 bucket "toluenetech-assets"
    - Bound as env.ASSETS in the Worker.
    - Used by /media/upload and /media/item/:id.
    - NOT used by Admin UI upload flows (Admin still uses Firebase Storage).

(d) Dahl Inference
    - AI provider for all three Tolesh surfaces + AI Lab.
    - Auth: Bearer token in env.AI_API_KEY (secret); AI_PROVIDER='dahl'.
    - Models: deepseek-ai/DeepSeek-V4-Flash-0731 (fast), MiniMaxAI/MiniMax-M2.7
      (reasoning), zai-org/GLM-5.3-Flash (fallback).
    - Kimi removed (retired).
    - No model keys in the browser.

8. DUPLICATE / REDUNDANT FEATURES
--------------------------------------------------------------------------------
- Lead storage is duplicated (Firebase leads collection AND Neon leads table),
  with write-only sync from Firebase→Neon on addLead(). The admin panel reads
  Firebase, Tolesh reads Neon; lead status changes made in the admin panel
  (updateLead) do NOT propagate to Neon, so Tolesh stats become stale.
- Project storage is duplicated (Firebase projects collection AND Neon projects
  table). Portfolio UI reads Firebase; Tolesh reads Neon.
- Media storage is duplicated: brand assets, project images, and founder image
  still go to Firebase Storage, while /media/upload writes to R2.
- The password constant 'iloveesther221@@' exists in BOTH context/AuthContext.tsx
  (frontend) and as DEFAULT_ADMIN_PASSWORD in server/src/lib/auth.ts; the env
  override only works for direct API calls, not for the UI login.
- Two separate Markdown/AiReply rendering paths: Markdown component in
  lib/markdown.tsx is used by ToleshChat AND by the new AILab — good. But any
  future messaging view would need to remember to use it.
- Session persistence is duplicated: sessionStorage tt_admin_session for admin,
  localStorage tt_{mode}_sid for Tolesh per-surface anon ids, localStorage
  tt_client_session for client auth — three different stores for related state.
- "Online" green pill in the admin header is hard-coded — it does NOT reflect
  actual Worker/DB/Firebase health (unlike /healthz which actually probes).

16. SECURITY / AUTH OBSERVATIONS (non-exhaustive, observed during audit)
--------------------------------------------------------------------------------
- Admin password is hardcoded in frontend JS and stored in plaintext in
  sessionStorage; env ADMIN_PASSWORD override is bypassed by the frontend login.
- /media/upload has NO authentication.
- JWT signature verification is not performed (structural + DB membership only).
- CORS_ORIGIN includes wildcard patterns ( *.netlify.app, *.pages.dev) that are
  string-matched, not wildcard-aware in the current cors.ts — verify this works
  for deploy previews.
- The ASSISTANT_SECRET env var is exposed in wrangler.toml vars (i.e. NOT a
  secret) — it is no longer used by the new assistant routes (they use the
  auth middleware instead) but it still ships to the client as a binding.
- No CSRF protection on POST endpoints (relies on CORS allowlist + SameSite).
- Lead creation on /leads is rate-limited but email validation is basic regex;
  no captcha / turnstile — could be hit by bots.
